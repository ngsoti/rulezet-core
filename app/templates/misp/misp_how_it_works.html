What is MISP?

MISP is an open-source threat intelligence platform (TIP) for sharing, storing and correlating indicators of compromise, malware, and detection artifacts across organizations. Information is organized into Events — containers grouping related Objects (structured, templated bundles of attributes) and Attributes.

This integration takes a Rulezet detection rule (any format) and compiles it into a MISP Object using the rule's own object template (yara, sigma, suricata, …), pairs it with a rulezet-metadata object describing the rule itself, then pushes the result to a connected MISP instance via its REST API.

Setting up an instance

Adding an instance requires an admin account. You'll need the instance's URL and an API key generated from your MISP user profile.

Field Description
Name Display name shown in the instance table.
URL The base URL of your MISP instance, e.g. https://misp.example.org — no trailing slash.
API key From your MISP user profile → Auth keys. Grants full API access as that user — encrypted at rest here.
Verify TLS Enabled by default. Disable only for a self-hosted instance presenting a self-signed certificate.
After creation, use the Test connection button (reads the instance's version) to verify it's reachable and the API key is valid.

The REST connection

MISP's API is a standard REST/JSON API, authenticated with a bearer API key. Rulezet talks to it through PyMISP's ExpandedPyMISP client.

1
Build the client
ExpandedPyMISP(url, api_key, ssl=verify_tls) is built from the stored URL and the decrypted API key.
2
Confirm connectivity
A single GET servers/getVersion call ("Test connection") confirms the URL and key actually authenticate before any push is attempted.
3
Push the event
A single POST client.add_event(event) call creates the Event (with its Objects) on the remote instance in one request.
4
Detect a rejected event
PyMISP doesn't raise for a rejected event — add_event() returns the created MISPEvent on success, or a plain error dict otherwise. Every push checks the return type explicitly rather than assuming success.
An SSL verification error almost always means the instance uses a self-signed certificate — disable Verify TLS for that instance if you trust it, rather than disabling verification globally.

Rule → Object/Event generation

Before anything is sent to an instance, the rule is compiled into a rulezet-metadata MISP object (title, version, author, license, tags, CVE/ATT&CK references, …) plus a format-specific content object, linked together by a related-to reference.

Rule format MISP object template
YARAyara — raw rule + rule name.
Sigmasigma — raw rule (typed sigma attribute, to_ids) + rule name.
Suricatasuricata — raw rule (typed snort attribute) + source link.
Wazuhwazuh-rule — raw rule + rule id.
NSE, CRS, NOVA, othersA dedicated or generic fallback object carrying the raw rule content.
This is the exact same generation code already used for the read-only "MISP Object"/"MISP Event" tabs on a rule's detail page — pushing doesn't change what's generated, only where it ends up.

Object vs Event push

MISP's API has no way to push a standalone Object without an Event to contain it — an Object always belongs to an Event. So both push buttons ultimately create a new remote Event; they differ only in how much is included.

Push as MISP Object

From the rule's MISP Object tab. Sends the lean Event containing just the rulezet-metadata + content objects.

No event-level tags or CVE attributes
Push as MISP Event

From the rule's MISP Event tab. Sends the same objects, plus the rule's tags (added as Event tags) and any CVE ids (added as vulnerability attributes, referenced from the content object).

Full context included
Neither push attaches to an existing remote Event — every push, of either kind, creates a brand new one. Pushing the same rule twice creates two separate Events on the instance.

Push lifecycle

Clicking Push on a rule's detail page (MISP Object/Event tab, admin only) queues a background job of type misp_push — it does not block the request.

1
Job queued
A misp.push_triggered activity log entry records the triggering admin, the target instance, the push type, and the job UUID.
2
Instance & rule lookup
The handler loads the target instance (must be active) and the rule (via the standard rule_core.get_rule(), respecting soft-deletion).
3
Object/Event generation
The rule is compiled to a MISPEvent as described above. Failure here fails the job immediately without attempting a connection.
4
Push via add_event()
The event is sent to the instance in a single REST call.
5
Completion
last_push_at and pushes_count are updated on the instance row, and a misp.push_done activity log entry records the outcome.

Credential security

A leaked MISP API key grants full API access to that instance as the key's owning user — a much larger blast radius than a typical read-only integration. Because of that, this feature deviates from the plaintext-credential convention used elsewhere in Rulezet:

Encrypted at rest

The API key is encrypted with Fernet before being stored, using a key derived from MISP_ENCRYPTION_KEY (or, if unset, a SHA-256 of SECRET_KEY as a zero-config fallback).

Never returned to the client

The instance's to_json() never includes the API key — the instance table and edit form only ever show the URL and status, never the secret itself.

This feature is admin-only, gated by the same before_request pattern as Connectors and Velociraptor. Only add instances you trust every admin on this instance with — anyone with admin access can trigger a push.
