What is Velociraptor?

Velociraptor is an open-source endpoint monitoring, digital forensics and incident response (DFIR) platform. It deploys lightweight agents ("clients") to endpoints and lets responders run VQL (Velociraptor Query Language) — a SQL-like language — against them, live, at fleet scale: process listings, file system scans, YARA memory/disk scans, Windows event log and ETW monitoring, registry inspection, and more.

Detections are packaged as Artifacts — YAML documents describing parameters and one or more VQL sources. This integration takes a Rulezet detection rule (YARA or Sigma) and compiles it into a Velociraptor Artifact, then registers that artifact directly on a connected Velociraptor server so it's immediately deployable to your fleet.

Nothing is deployed to endpoints automatically. Pushing an artifact only registers it on the server — an operator still needs to run a Hunt or a client-targeted collection from the Velociraptor GUI to actually execute it on endpoints.

Setting up a server

Adding a server requires an admin account. The credentials come from a Velociraptor API client config — generate one on your Velociraptor server with:

velociraptor config api_client --name rulezet --role administrator rulezet.api_client.yaml
Field Description
Name Display name shown in the server table.
API connection string The api_connection_string field from the API client config — a bare host:port, e.g. 127.0.0.1:8001. Not the GUI URL (a different port, typically 8889) and no https:// scheme — gRPC targets are bare host:port.
CA certificate The ca_certificate field — public, not sensitive.
Client certificate The client_cert field — grants API access, encrypted at rest here.
Client private key The client_private_key field — grants full API access, encrypted at rest here.
Each certificate/key field can be pasted directly or loaded from a file with the "Upload file" button next to it — both end up as the same plain text field, no separate upload endpoint.
After creation, use the Test connection button (SELECT Hostname, OS, Platform, PlatformVersion FROM info()) to verify the server is reachable and the credentials are valid.

The gRPC connection

Velociraptor's API server speaks gRPC over mutual TLS — both sides present a certificate. Every request Rulezet makes follows the same pattern:

1
Build mTLS credentials
grpc.ssl_channel_credentials() is built from the stored CA certificate, client certificate, and (decrypted) client private key.
2
Open a secure channel
grpc.secure_channel(api_connection_string, creds, options) — with grpc.ssl_target_name_override="VelociraptorServer", required because Velociraptor's server certificate CN doesn't match an IP target.
3
Run a VQL query
A single gRPC APIStub.Query() call streams back response chunks — each one either JSON row data or a log line.
4
Detect silent VQL errors
A bad query can return zero rows with no gRPC exception at all — the compile error only appears as an ERROR:-prefixed log line. Every query checks for that case explicitly and raises if rows are empty and an error was logged.
A Received http2 header with status: 307 gRPC error almost always means the connection string points at the wrong port — most commonly the GUI port (redirects to a login page over plain HTTP/2) instead of the real API port from the client config.

Rule → artifact generation

Before anything is sent to a server, the rule's raw content is compiled into a Velociraptor Artifact YAML document. The exact shape depends on the rule's format.

YARA rules

Compiled into a CLIENT-type artifact named Rulezet.Detection.YARA.<Title> with two VQL sources:

  • ProcessScan — scans every running process's memory via foreach(row={SELECT ... FROM pslist()}, query={SELECT ... FROM proc_yara(...)}), gated by the ScanProcesses parameter.
  • DiskScan — scans files matching a configurable TargetGlob parameter via FROM yara(rules=YaraRule, files=TargetGlob), gated by ScanDisk.
Sigma rules

Compiled into a CLIENT_EVENT-type artifact named Rulezet.Detection.Sigma.<Title>, using Velociraptor's built-in sigma() VQL plugin with a log_sources mapping derived from the rule's logsource.category.

process_creation → watch_etw() mapped other categories → flagged placeholder
For Sigma categories other than process_creation, the generated artifact still compiles, but its log source is a clearly-marked TODO placeholder rather than a guessed ETW GUID — an unverified mapping would be worse than an honest gap. Both the artifact's description and its VQL comment flag this before deployment.
Every generated artifact's description includes the rule's UUID, a link back to its Rulezet detail page, its author, and its tags — so anyone browsing artifacts on the Velociraptor server can trace it back to its source.

Push lifecycle

Clicking Push on a rule's detail page (Velociraptor tab, admin only) queues a background job of type velociraptor_push — it does not block the request.

1
Job queued
A velociraptor.push_triggered activity log entry records the triggering admin, the target server, and the job UUID.
2
Server & rule lookup
The handler loads the target VelociraptorServer (must be active) and the rule (via the standard rule_core.get_rule(), respecting soft-deletion).
3
Artifact generation
The rule is compiled to Artifact YAML as described above. Failure here (e.g. unsupported format) fails the job immediately without attempting a connection.
4
Registration via artifact_set()
The artifact is registered with SELECT artifact_set(prefix='Rulezet', definition=ArtifactYAML) AS Result FROM scope(). artifact_set() is a VQL function, not a plugin — calling it as a table source (FROM artifact_set(...)) silently compiles to zero rows with no error.
5
Completion
last_push_at and artifacts_pushed are updated on the server row, and a velociraptor.push_done activity log entry records the outcome.

Format support

Only formats with a real, verified VQL mapping are supported — the Velociraptor tab (and its "Push" control) only appears on a rule's detail page when its format is supported.

Format Support
YARA Supported — process memory + disk scan.
Sigma Supported — process_creation fully mapped, other categories flagged for manual completion.
Suricata, Zeek, others Not supported — no verified VQL equivalent yet.

Credential security

A leaked Velociraptor client private key is impersonation-capable against your entire endpoint fleet — a much larger blast radius than a typical API key. Because of that, this feature deviates from the plaintext-credential convention used elsewhere in Rulezet:

Encrypted at rest

client_cert and client_private_key are encrypted with Fernet before being stored, using a key derived from VELOCIRAPTOR_ENCRYPTION_KEY (or, if unset, a SHA-256 of SECRET_KEY as a zero-config fallback).

Never returned to the client

The server's to_json() never includes certificate or key material — the server table and edit form only ever show the connection string and status, never the secrets themselves.

This feature is admin-only, gated by the same before_request pattern as Connectors. Only add servers you trust every admin on this instance with — anyone with admin access can trigger a push.
