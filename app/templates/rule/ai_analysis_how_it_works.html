How AI Rule Analysis Works

A complete walkthrough of the AI-assisted rule summary feature — from the background job that generates it, to exactly how a locally-hosted model is kept from ever leaving the server or inventing facts.

What is AI Rule Analysis?

A background job (admin-triggered, same job system as GitHub imports or MISP updates) that runs a locally-hosted Ollama model over a selection of rules — or every rule on the instance — and writes a detailed English Markdown report explaining, in plain language, what each rule does and why it matters.

This is currently Phase 1 of a larger plan: summary generation only. It does not (yet) suggest tags or ATT&CK techniques, and it never touches CVE data — see Roadmap below.

Job lifecycle

Triggered from the AI Rule Analysis tab on /account/admin/bulk_parse_fields (admin only) — picking rules reuses the same rule selector as every other bulk admin tool, choosing a model from the admin's own allowlist (see Configuration), and queues a background job of type ai_rule_analysis.

1
Feature & local-only guards
Before touching a single rule, the job checks the instance-wide enabled switch, that the chosen model is still in the admin's enabled list, and that OLLAMA_URL looks like a local/private address. Any failure refuses the whole run up front — see Security & privacy.
2
One rule at a time
Unlike other bulk jobs (which batch hundreds of rows per commit), this job processes one rule per Ollama call, checking for pause/cancel before every single one — a local model can take tens of seconds to a few minutes per rule, so responsiveness matters far more here than raw throughput.
3
Already-analyzed rules are skipped, unless told otherwise
Unless "regenerate existing" was checked, a rule that already has at least one analysis is skipped (counted separately in the log) rather than re-analyzed — a re-run only ever fills in gaps. Checking it doesn't overwrite anything either — it just adds another row to that rule's history.
4
Stored as a new history row
A RuleAiAnalysis row is created — plain Markdown content, which model produced it, who triggered the run, and a visibility flag (public by default) — never as pre-rendered HTML. See Prompting & validation.
5
Displayed on the rule's own AI Analysis page
/rule/detail_rule/<id>/ai_analysis renders the latest analysis client-side through marked.parse() + DOMPurify.sanitize() — the exact same pipeline blog posts already use — with the full history browsable below it, and a note showing which model wrote it, when, and who requested it.

Prompting & validation

Rule content comes from any authenticated user — it is treated as untrusted, attacker-reachable data at every step, never as instructions.

The system prompt

Explicitly frames the rule content block as data to summarize, tells the model to ignore anything inside it that looks like an instruction, forbids inventing facts not present in the rule (no guessed CVEs, actor names, or version numbers), and requires a strict JSON envelope ({"summary": "..."}) via Ollama's format: "json" — a weak model rambling in free text never reaches storage.

Post-generation checks

The response must parse as JSON, contain a non-empty summary string, and stay under a sanity length ceiling — an unusually long response is treated as a degenerate repetition loop (a known small-model failure mode) and discarded, not stored. Stray control characters are stripped before anything is written.

The rule's raw content is also truncated before it reaches the model — a local model's context window is shared between the system prompt, the rule content, and the response itself. An unbounded rule body would silently eat into the model's own instructions instead of raising a clear error.
The stored summary is always raw Markdown text, never HTML. Rendering only ever happens in the browser through marked + DOMPurify, the same as blog posts — this is what actually stops a prompt-injected rule from getting a <script> tag into its own "AI summary," not escaping at storage time.

Failure handling

Not every failure means the same thing, so the job treats them differently:

Situation What happens
One rule times out Skip & continue — logged as a warning, the job moves to the next rule. A slow rule never stalls the whole run.
Model returns invalid output Skip & continue — not valid JSON, missing the summary field, or absurdly long. Nothing invalid is ever stored.
Ollama is unreachable Stop the whole job — every remaining rule would fail identically, so the job fails cleanly instead of burning through the rest of the run logging the same error. The current position is saved.
Job paused, cancelled, or the server restarts Resumable — see Built for scale.

Built for scale

Rulezet instances can hold hundreds of thousands of rules. A local model generating one summary at a time is fundamentally slow — no application-level trick changes how fast a single Ollama instance can generate text — so the engineering focus here is on correctness and resumability over an unattended run that may last days, not on pretending a weak local model is fast.

Stable pagination

The query behind the job is never filtered by "doesn't have a summary yet" in SQL — doing so would shrink the result set as rows are processed and silently skip rules under plain offset pagination. The target set is fixed for the whole run; "already has one, skip it" is a per-row check in code instead.

Survives a restart

This runs through Rulezet's real BackgroundJob system, not a throwaway in-memory session — its offset is persisted after every single rule. If the server restarts mid-run (a deploy, a crash), the worker automatically recovers the job back to pending and it resumes from exactly where it left off, instead of losing days of progress.

Practical advice for a large instance: start with a small selection to validate quality and timing on your hardware/model before ever queuing "ALL rules" — the job's live log shows a running count of generated/skipped/failed rules so you can judge throughput early rather than waiting for the whole run.

Configuration

Variable Purpose
OLLAMA_URL Same Ollama instance the chatbot uses. Defaults to http://localhost:11434. Must resolve to a local/private address — see Security & privacy.
OLLAMA_MODEL_RULE_ANALYSIS Fallback default only — the admin picks a specific model per run from the AI Rule Analysis settings page, which lists whatever Ollama actually has pulled. This env var only matters for direct/manual calls that don't go through the trigger UI.
AI_RULE_ANALYSIS_TIMEOUT Per-rule timeout in seconds (default 600 — the report format is a detailed, multi-section writeup with tag/ATT&CK/CVE context, not a one-line summary, and can take several minutes on CPU-only hardware). A rule that takes longer is skipped, not failed — see Failure handling.
The admin settings page is where the feature is actually managed day-to-day: an instance-wide on/off switch, a per-model enable/disable allowlist synced from Ollama's own model list, and a searchable history across every rule with bulk delete.

Security & privacy

Local-only, enforced

The whole point of using Ollama locally is that rule content never leaves the server. Before the job touches a single rule, it checks that OLLAMA_URL resolves to localhost, a .local hostname, or a private (10.x/172.16-31.x/192.168.x) address — and refuses to run at all otherwise, so a misconfigured OLLAMA_URL can't silently turn this into a data-exfiltration path.

Triggering & moderation are admin-only

The trigger tab, the trigger route, the settings page (feature toggle + model allowlist), and every moderation action (visibility toggle, delete, bulk delete) are all gated on current_user.is_admin() — the same pattern as every other bulk admin tool. Regular users only ever see a finished, public analysis on a rule's own page — never a way to trigger or moderate one themselves.

An LLM can write something wrong, embarrassing, or worse — this is treated as a real possibility, not a hypothetical. Every RuleAiAnalysis row has its own is_public flag (visible by default). An admin can flip a single bad generation to private from either the rule's own AI Analysis page or the cross-rule history table on the settings page — it disappears from what regular users see immediately, without deleting the row itself (so it stays reviewable). Deletion is a separate, explicit action for when hiding isn't enough.
Log lines never include full rule content or the model's full raw response — only the rule id and a short outcome (generated / skipped / failed), so the job's log stays readable and doesn't balloon into a second copy of your entire rule corpus.

Roadmap

What's live today vs. what's planned but not yet built:

Live Phase 1 — Markdown summary generation (this page).
Planned Phase 2 — tag suggestions, constrained to tags that already exist in the DB, never invented.
Planned Phase 3 — ATT&CK technique suggestions by name, same constrained-choice approach as tags.
Out of scope CVE detection or suggestion by the model — local LLMs are prone to inventing CVE identifiers, which is actively harmful on a real detection rule. If ever revisited, only literal-token extraction (like the existing regex-based detect_cve()) would qualify, never model judgment.
