What is Rulezet AI?

Rulezet's AI features are all powered by a self-hosted Ollama instance — there's no third-party API key, no per-token billing, and nothing leaves the instance. Four independent agents share one architecture: a Chatbot assistant, a Rule Analysis summarizer, a Rule Generator (Beta, YARA-only), and a Rule Fixer. Each one is a thin, single-purpose wrapper — a system prompt, a bit of parsing logic, and a call into existing rule/bundle code. None of them re-implement anything Rulezet already does; they just decide when to call it.

Every agent runs on whatever model the instance admin configures — often a small, fast model. Small models are unreliable at strict structured output, so every agent leans on deterministic code, not model trust, wherever a wrong answer would actually matter. That design choice shows up throughout this page.

The shared architecture

All four agents extend the same base class and go through the same pipeline before a single token is ever generated.

1
One agent, one class
Every feature is a small class implementing a shared AIAgent interface — its own system prompt, its own way of turning a request into messages, and its own way of parsing the model's reply back into something usable. Adding a new AI feature means writing one new class, not touching the pipeline.
2
Feature flag & rate limit
Before anything else, the agent checks whether it's enabled for this instance (an admin kill switch) and whether the calling user is under their per-hour rate limit. Both are configurable per agent — batch/admin-triggered agents like Rule Analysis have no per-user limit by design.
3
Concurrency governor
Ollama runs on the instance's own hardware, so a slot-based governor caps how many model calls run at once — a burst of requests queues instead of falling over.
4
The model call
A shared Ollama client sends the prompt to whichever model this agent is configured to use (an explicit per-agent choice, or the instance's global default) and reads back a response.
5
Every call, logged
Success or failure, every single call — which agent, which user, which model, how long it took, and whether it looked suspicious — is written to one shared execution log, visible to admins on the Models & Security page.
The model itself is swappable per agent from a shared allowlist synced straight from Ollama's own model list — disabling a model there removes it from every feature's dropdown at once.

Security & guardrails

Rule content and user descriptions are untrusted input the moment they reach a model — they're framed as data, never as instructions, and scanned for prompt-injection patterns before the call is made.

Untrusted-data framing

Anything a user typed — a rule's content, a plain-language description — is wrapped with an explicit preamble telling the model it's reading data, not commands. This is the same principle as any prompt-injection defense: content can describe what to detect, it can never instruct the assistant to do something else.

Injection scanning

The full input (not just a truncated preview) is scanned for injection-shaped phrasing before the call. A flagged request still runs — the framing above already neutralizes it — but the flag is visible to admins in the execution log, so a pattern of attempts stands out.

Per-feature kill switch

Any of the four agents can be disabled instance-wide from the AI Overview page — instantly, no restart needed — either one at a time or all at once.

Per-user rate limits

Interactive agents (Chatbot, Rule Fixer, Rule Generator) cap how many calls a single user can make per hour. Rule Analysis is admin/batch-triggered and isn't rate-limited the same way.

No agent is ever allowed to invent a value it wasn't given. Rule Generator and Rule Fixer only ever propose drafts — nothing is saved until a human reviews it and clicks Save. The Chatbot's create-rule action refuses to run unless the exact content it's about to save actually appears in what the user typed.

Chatbot

Prototype
{% if mascot_enabled %}
This one's me, in the little widget in the corner. I don't do real "tool calling" — I ask the model to reply with a small JSON envelope instead: one action, plus whatever it needs to run it.
{% endif %}

Every message is sent with a system prompt describing five possible actions — create_rule, create_bundle, navigate, search_rules, or plain chat/ask — and the model replies with exactly one of them as JSON. The backend never re-implements rule/bundle logic itself; it just calls straight into the same rule_core/bundle_core functions the rest of the site uses.

Small models are inconsistent at this JSON-classification task — a plain "hi" can get echoed back verbatim, a clear "create a bundle called X" can get answered with the raw JSON template's own placeholder text instead of an actual bundle. Every one of these failure shapes, once found, gets a deterministic pattern match that answers correctly without ever calling the model — greetings, "who are you", search filters (tag/CVE/ATT&CK id/author/source URL), navigation destinations, and create-rule/bundle intent are all handled this way today. The model is only asked when nothing else recognizes the message.
search_rules

Builds a link to the same filtered rule list you'd reach by clicking filters yourself — tag, CVE, ATT&CK technique, author/editor, GitHub source, or a free-text topic. No search API is called; it's a plain redirect with the right query parameters, plus a real result count so the reply is honest about whether anything actually matched.

create_rule

Requires the actual rule content to already appear in what the user typed — nothing is ever invented. Goes through the exact same parse-and-validate path as the "Parse" tab on the create-rule page, so duplicate detection and syntax errors behave identically.

create_bundle

Needs just a name (description optional) — calls the same bundle-creation function the manual bundle form uses.

navigate

Picks from a fixed, closed list of page destinations — never a raw URL the model could invent. Admin-only destinations are re-checked against the actual requesting user's permissions server-side, regardless of what the model decided.

Rule Analysis

{% if mascot_enabled %}
An admin points me at a rule, I read its content, tags, and ATT&CK mapping, and I write up what I find in plain English. That's the whole job — I'm a summarizer, not a critic with opinions I haven't earned.
{% endif %}

Triggered by an admin from a rule's detail page (or in bulk as a background job). The rule's content, tags, and MITRE ATT&CK associations are handed to the model with a prompt asking for a factual, plain-English write-up — what the rule looks for, and how. The output is saved as one entry in that rule's analysis history, and can be toggled public or admin-only.

Admin-triggered and batch-friendly — this is the one agent without a per-user rate limit, since it's never run by an arbitrary visitor.

Rule Generator

Beta — YARA only
{% if mascot_enabled %}
Tell me what you want to detect, I draft a YARA rule for you — one attempt, no back-and-forth retries. You always land on the Manual tab afterward to actually read it before it becomes real. I've never once been offended by an edit.
{% endif %}

You describe what the rule should detect (plus an optional sample string or pattern to ground it), and the model drafts YARA content in one shot — deliberately no retry loop. A quick compile check runs afterward as an informational signal only (shown to you, never blocking) — re-validating in a loop would cost real time for a feature that's already asking you to review the result by hand.

1
Describe it
A plain-language description, optionally with a sample to anchor the pattern.
2
One draft, one pass
The model writes the rule once. A syntax check runs and its result is shown, but never blocks you from using the draft.
3
You review, always
The draft lands on the Manual creation tab — title, description, and source pre-filled — fully editable, never auto-published.
YARA-only for now, and marked Beta — the model can and does get pattern details wrong sometimes. Treat every draft as a first pass, not a finished rule.

Rule Fixer

{% if mascot_enabled %}
I've fixed worse rules than yours. Probably. Click me on a broken rule's edit page, I read the exact validator error and propose the smallest fix I can as a diff — one try, then it's your call.
{% endif %}

Shown on a rule's edit page whenever it fails validation. One click sends the broken content and the exact validator error message to the model, which proposes a minimal fix as a diff against your original content. Like the Generator, this is deliberately one attempt, no retry loop, no automatic re-validation — you decide whether the fix is right and click Save yourself.

The fix is never applied automatically. You get a side-by-side diff and a short explanation of what changed — nothing touches your rule until you review it and save.
